# Deslop contract

The supported environment is macOS and Linux with github.com.

Every passing push to `main` publishes a GitHub release with `deslop.tgz`. Release workflows queue serially. The version is one patch above the highest existing stable `vX.Y.Z` tag, ignoring legacy commit-suffixed tags; without a stable tag, the starting version comes from `package.json`. The first stable release is `v0.1.1`. The workflow updates the packed package's version, tags the pushed commit and never commits back to `main` or replaces a tag or asset. The installer accepts stable version pins and legacy commit pins. Existing releases stay available.

Deslop works on commits, without requiring a push or pull request. A dirty checkout stops with one line: `commit or stash your changes first`. It refuses the default branch. There is one flow, with fixing as its only behavior.

1. A fresh non-interactive agent reviews the branch diff without check results, fixes every finding and writes all of its findings as plain text into the run's review file. Only deslop can stage, commit, push or write markers. The agent's tools deny git operations; deslop also rejects unexpected git-state changes. Edits become `deslop: fix review findings` commits as the configured user, with no attribution footer.
2. Deslop runs the selected commands locally. When the original commit is already pushed and selected kinds require CI, it pushes only its own fix commits to that same branch and waits for the named checks on that exact commit. `--local` forces local commands and keeps fix commits local. A kind with `ciRequired: true` runs local commands even for a pushed run, then its named CI checks on the final exact head only after every local command passes. Local failures resume the agent with trimmed failures before any required-CI wait. An unpushed required-CI head ends red with a push/rerun hint and posts nothing to GitHub. Missing CI never counts as passed. Checks and statuses with the same name must both pass. GitHub identity comes from origin, including when gh has another default repository. Fix pushes require the observed remote SHA to remain unchanged and advance it only to a descendant.
3. Failed checks return trimmed failure details to the same agent session, resumed by id. Deslop commits edits as `deslop: fix failing checks` and reruns checks. `checkFixAttempts` defaults to 1; 0 returns failures without another agent call. Exhausting attempts leaves no marker. A custom command without resume support receives a fresh call describing prior changes.
4. The optional try step runs once, after the checks first pass. It is off unless configured:
   - Mode: each kind's `try` is `none` (the default), `code` or `ui`, and the run uses the highest mode among its selected kinds.
   - Override: the intent's "How to try this" section may start with `Try: none|code|ui` (bold, code or bullet formatting allowed) to set the mode for that run. Any other value stops the run with a usage error. The rest of the section, without HTML comments, is the agent's guidance.
   - `tryNotes`: a repo-level string that tells the agent how to run the app, passed through as text. Deslop starts no app or browser itself.
   - Turn: the same session resumes with the mode and guidance. `code` exercises the changed behavior directly (calling functions, running the CLI, hitting the API with real cases); `ui` also starts the app and drives it in a headless browser of the agent's choice, stopping what it started before the turn ends. The turn uses the agent timeout.
   - Tools: commands are allowed but git and gh are not. Claude gets Bash with `git` and `gh` denied; Codex gets its shell tool, network and read access to ignored paths except `.deslop`. Both get a temporary scratch folder outside the repository, also used as `TMPDIR`, `GH_CONFIG_DIR` and `DESLOP_TRY_DIR`, and git runs with every transport disabled. Shell access is not a sandbox: the git-state guard still applies, and Bash can read `.deslop` logs during this turn. Deslop deletes the folder after the turn.
   - Fixes: tracked-file edits become `deslop: fix try findings` and the checks rerun, sharing the `checkFixAttempts` budget for any later failures. New untracked files in the repository end the run red (`TRY_FILES`), and config or instruction edits end it red (`PROOF_EDIT`), both left uncommitted.
   - Result: the agent appends what it tried and found to the review file's findings. A failure it could not fix goes in `unfixed.md` in the scratch folder; deslop then adds a failed `try` check, ends red, prints the text and leaves no marker. Otherwise the verdict still comes from the checks. The record's `try` field holds the mode, its source (`kind` or `intent`), the turn's seconds and any unfixed text.
5. Success adds a git note under `refs/notes/deslop` to the final commit. A GitHub status named `deslop` requires that final commit to be pushed. Local publication defaults off (`publishLocal: false`); `status --publish` verifies green CI on the exact commit. `publishLocal: true` permits successful local checks to publish, but never bypasses a ciRequired kind. Markers never describe another commit. Deslop never merges or pushes to the default branch.

The reviewer prompt's first section is the intent: the `--intent <file>` contents, otherwise the open PR's description read through `gh`, each capped like other prompt inputs. A missing or blank `--intent` file stops the run with a usage error. With neither, it states that no intent was supplied, so every code smell is unasked. Check-fix prompts repeat the same section. Immediately after intent, the first-review prompt lists every added comment line in the reviewed diff as `file:line: text`; `clean` lists every comment in the reviewed files instead. Collection uses TypeScript token trivia from its parsed syntax tree for JS/TS (including JSX/TSX), avoiding strings, regular expressions and literal template/JSX text. Other supported extensions use simple per-extension rules: lines that start with a comment marker, plus the following lines of a block comment opened on such a line, without promising inline or full block parsing. Deleted, binary and symlinked files are skipped. The inventory is deterministic, ordered by file and line, uncapped and collected before the reviewer runs. The selected skills tell the agent how to resolve it; collection makes no keep/delete judgment. The run record names the intent source (`file` with its path, `pr` with its number, or `none`).

Commands: `deslop run` (also bare `deslop`), `deslop clean <path>...`, `deslop init`, `deslop status`, `deslop skill copy <name>`, `deslop shape`. `skill copy` writes a shipped skill to `.agents/skills/<name>/SKILL.md` and refuses when that file or the `.claude` one exists. Base selection is explicit `--base`, then an open PR's base branch, then origin's default branch, then local main/master. PR lookup is optional; local repositories work without GitHub.

`deslop clean <path>...` replaces the branch diff with every tracked file under the given paths. The prompt lists those paths without their contents and the agent reads them itself, so no size cap applies. Kind selection, instruction grants and the lint scope use those files plus the run's own edits; checks, commit messages, check fixes, proof and default-branch refusal match `run`. Paths are resolved from the current directory and stored relative to the repository root; a path outside the repository is refused. The record and the proof note carry `mode: "clean"` and those `paths`, and `deslop status` prints them; `run` records have `mode: "run"`.

Configuration contains commands, change kinds with command/check/instruction/try selection, `tryNotes`, instruction-file overrides, checkFixAttempts, custom provider commands, per-provider model/effort and agentTimeoutMinutes. Configuration lives in the repository; machine settings contain only agent preferences. The first matching kind applies per changed path; requirements are unioned across paths, including both sides of renames. Agent selection uses CLI override, then machine preference/list, then the detected caller. Model and effort use CLI override for the primary provider, then machine, then repo, then provider default. Fallback providers use their own settings.

Machine state lives in `~/.deslop`: `settings.json`, and per repository `repos/<repo>/reviews/` and the optional `repos/<repo>/skills/`. `<repo>` is origin's repository name, or the checkout folder without an origin. Each run's review file is `repos/<repo>/reviews/<YYYY-MM-DD>-PR-<n>.json`, or `<YYYY-MM-DD>-<branch>.json` without an open PR; a repeat for the same PR or branch on the same day adds `-2`, `-3` and so on. Deslop creates it empty at that final path before the reviewer runs. The prompt names it and tells the agent to fix every finding and write all of them there as plain text, in any form; Codex and Claude may write exactly that file on top of their normal editing scope; custom providers also get its path in `DESLOP_FINDINGS_FILE`. A provider that fails before editing and falls back leaves the file as it found it. After the agent ends, deslop reads the text and rewrites the same file as its record, with no further agent call: date, repo, branch, PR, mode, intent source, verdict, checks with name/ok/log/failures, commits, and `findings` holding the agent's text verbatim. A missing or empty text means no findings. Check-fix turns resume the same session with the findings text back in the file and add their own before the next rewrite. Check logs and per-turn agent output stay under git-ignored `.deslop/runs/<id>/`; each check's `log` in the record is an absolute path, and the proof note's `run` field names the record. Each failure has test, message and an excerpt of at most 20 lines; full output stays in separate log files. Pass or fail comes only from the checks and deslop's git-state and scope guards, never from the findings. The short terminal summary lists checks, the findings text (or a pointer to the review file when it is longer than 20 lines), commits, the record path, `deslop shape`, and warns that full logs can be large. Shape prints a small example and identifies fields that may be long.

A rerun preserves proof until a red check verdict; then it removes the current note and attempts to publish failure together. It never posts a pending status. GitHub publication outages retain a successful local note, with a retry hint. Poll errors retry within the bounded CI wait; missing and non-code final states end red without a repair call. Only failure, error and timed_out are fixable. A repair with no edits ends red without repeating checks.

Neither provider loads AGENTS.md or CLAUDE.md implicitly. Repositories may select either explicitly through instruction overrides. Outside try turns, Claude cannot read `.deslop` logs. Prompts cap additional changed-file content per file and in total. Local commands retain their 15-minute timeout. Reviewer agent calls (initial review, clean, each check-fix turn and the try turn) default to 45 minutes per provider call. `--agent-timeout <minutes>` overrides machine `agentTimeoutMinutes` in `~/.deslop/settings.json`, then repo `agentTimeoutMinutes`, then the default. Values are positive finite numbers, allowing fractional minutes, with a maximum delay of 2,147,483,647 milliseconds. A timeout ends the run red without retrying the agent; the summary and review record’s `error` identify the call (including the check-fix turn), provider, timeout in minutes and the setting that raises it. Command and agent processes terminate their process groups (the child tree on Windows) on timeout. Inherited output pipes cannot keep timeout completion waiting. Catchable interruption signals terminate active child groups before run ownership is released. Uncatchable process death can bypass cleanup; stale PID-lock recovery proves the owner died, not that every orphaned descendant exited.

`init --command name="command" --check "check name"` accepts repeated values; `init --config file` imports a configuration. Init also writes `.github/pull_request_template.md` with What was asked (the intent), What changed, How it was checked, How to try this, and a closed `<details>` Intentional slop section. Each intentional item names its file, what is kept and why. Existing PR templates (any extension or case in the root, `.github` or `docs`, including files directly inside `PULL_REQUEST_TEMPLATE` folders) keep all their content and receive only missing deslop sections. Existing headings or folded summaries identify sections without duplication. Symlinked templates and template directories are refused rather than followed, before init writes the config. `--no-pr-template` skips all template changes. Running deslop without init still requires no template. Missing required values prompt on a terminal and error with the flag otherwise. There is no machine-stored repository config.

After the initial review and completed command sequences, deslop reloads repo configuration before selecting checks for proof. Check-fix turns may not edit config or configured instructions. Such edits end red and remain uncommitted. Workflow edits appear in the summary. Failures report uncommitted paths in `left`.

Run deslop only on repositories you trust. Verification executes the repository's configured commands, executable ESLint configuration and tooling as your user, just like running its test suite. Editor permissions do not sandbox verification or edited execution policy.

Each checkout admits one writer through an atomically published, populated owner directory. Stale recovery reports and removes only provably dead owner names; legacy PID-file locks stop with a migration hint because older writers cannot be excluded atomically; removing an empty directory cannot delete a populated replacement.

The git-state guard covers this checkout’s HEAD, branch, staged index, the current branch configuration, origin remote, user, commit/signing settings and hooks. Enabled worktree configuration is also guarded. Other worktrees may commit to their own branches during a run. Provider tool restrictions still deny git operations; unrelated shared refs do not invalidate this checkout.

Tracked instruction prose in the reviewed diff receives file-level write grants, including protected agent-instruction directories. Existing untracked and ignored paths stay excluded; other instruction files remain read-only. Git metadata and git commands stay denied. New normal source/test files are allowed, committed by deslop, and listed in the run record's newFiles array. Codex uses a scoped permission profile; Claude uses native Edit permission rules. A post-edit scope check refuses instruction changes outside the reviewed diff.

Local checks run in order on the evolving tree. After each command, deslop commits all of its nonignored edits as `deslop: <command>`; each command has its own commit. When any command changes files, deslop runs the sequence once more as the proof pass. That pass decides the verdict by exit codes and commits its own edits the same way. Commands that still edit files in the proof pass are named as unstable in the summary. Deslop never loops until files stop changing or refuses command edits. There is no configuration option for this behavior.


## Review skills

Deslop ships three independent default skills in `skills/`:

- `review-code` checks correctness and bugs in changed code. Where the diff touches them, it checks plain domain names without abbreviations, consistent names across layers, project conventions and data model changes: table and column names, types, nullability, constraints, indexes, one source of truth and safe migrations.
- `kill-ai-slop` removes em dashes, AI-sounding filler and code comments, including exported-function doc comments. License headers and type annotations read by a type checker stay. Meaning from deleted comments moves into function, constant or variable names, or well-named extracted steps; only reasons that no name can carry go in the PR description. The reviewer resolves each supplied comment-list entry. The intent's Intentional slop section protects listed comments, workarounds and one-off values, unless a low-hanging clean alternative removes them; the reviewer applies that alternative and says so in findings. Unlisted comments and workarounds follow the usual rules. It treats lint/type silencing, empty or swallowing catches, blind retries, sleeps, arbitrary timeouts and special cases hardcoded for one input as defects. It fixes the real cause or removes the workaround, subject to the Intentional slop rule, with any reason in the PR description rather than a code comment. With no intent supplied, every smell is unasked. Product behavior choices are never judged as workarounds. It also removes dead code and one-caller wrappers, flattens needless nesting, prefers reuse and one place per rule, and keeps commit and PR text plain for a cold reader. For docs/prose it applies the writing rules.
- `audit-tests` checks the quality of existing tests and coverage of the key behaviors in the diff through the public surface. Tests survive renaming constants, functions and files. No test is needed for properties guaranteed by the type checker, wiring, configuration or framework behavior. New coverage folds into existing related tests before adding a test or file: a new login field goes in the existing login-flow test. Flaky tests are deleted when unnecessary or rewritten deterministically, never patched with retries, sleeps or longer timeouts. It flags missing coverage only for a real behavior a user or caller depends on: a meaningful new branch, failure path or boundary. It prefers deleting unnecessary tests and folding overlapping tests over adding more, adds only focused behavioral coverage, and does not chase coverage numbers, test trivial code or demand evidence the tool cannot produce.

Selection uses the first matching kind for each changed path. A code kind selects `review-code` and `kill-ai-slop`. Test paths (test/spec filenames and test directories) or an existing repository test suite add `audit-tests` to code review. Existing tests are detected from tracked conventional test filenames/directories, tracked paths selected by a `test`/`tests` kind, or a configured command named `test` or `tests`. Detection also covers non-JavaScript test suites. A docs/prose kind or a prose extension selects only `kill-ai-slop`. An explicit kind `instructions` list replaces this selection. Skills selected by different paths are unioned. The review prompt follows only those instructions; it does not impose a disabled concern through a separate built-in checklist. Legacy names `code`, `tests` and `writing` alias the corresponding shipped skills.

Instruction precedence is per skill: `DESLOP_INSTRUCTIONS` > a local per-repo skill > the repo `instructions` map > a same-name repo skill > shipped default. A local per-repo skill is a file at `~/.deslop/repos/<repo>/skills/<name>/SKILL.md` on the owner's machine; it replaces that skill for that repository only. A same-name repo skill is a tracked regular file at `.agents/skills/<shipped-name>/SKILL.md`, else `.claude/skills/<shipped-name>/SKILL.md`, and needs no config; ignored, untracked and symlinked files do not count. In `deslop.config.json`, `instructions` maps skill names to file paths relative to the repository, or `false` to disable that skill. Each default is independently replaceable or disable-able. For example, `{"instructions":{"review-code":"AGENTS.md","audit-tests":false}}` replaces correctness instructions and disables the test audit, keeping the cleanup default.

For uncommitted machine preferences, `DESLOP_INSTRUCTIONS` points to a JSON map with the same per-skill path-or-false values. Paths are relative to that JSON file's directory. Each entry wins over local per-repo skills, repo settings and defaults; omitted entries retain their lower-precedence values. This supports swapping or tweaking any one skill without modifying repo files. Invalid or missing instruction files stop the run. Neither AGENTS.md nor CLAUDE.md is loaded implicitly; Codex sets `project_doc_max_bytes=0`.

## Lint and type checking

Deslop's own source and tests are TypeScript that Node runs without a build step by stripping types, so they use only erasable syntax and `.ts` import paths. Node refuses to strip types under `node_modules`, so the installed command and the fallback lint worker start from plain JavaScript entries in `bin/` that load the TypeScript through jiti, with no install-time build. ESLint runs its recommended rules plus house rules: an object literal, destructuring pattern, type literal or interface with two or more entries puts each entry on its own line; unused variables/imports and em dashes in strings/comments are errors. `npm run lint` checks them and `npm run lint:fix` fixes layout. `npm run typecheck` runs `tsc --noEmit` over source, shipped lint code and tests. Deslop's config and both Node CI jobs run lint, type checking and tests.

For reviewed repos, lint precedence is:

1. The repo commands/CI active in this run take precedence. Deslop does not add another lint pass when an active command name, shell command or CI check name identifies `lint` or `eslint`. An optional CI lint check does not suppress fallback lint under `--local`, because it will not run. A local lint command skipped for CI also does not suppress the fallback.
2. Otherwise deslop runs its fallback ESLint on existing regular JS/TS files in the change scope, including new files created during the run. It does not lint unrelated files, deleted paths or files reached through symlinks. For each file, the nearest repo ESLint config wins (flat config or legacy eslintrc/package config); with none, deslop's shipped recommended/house config applies. A broken repo config fails the check rather than silently using the default.
3. `fallbackLint: false` disables the fallback, including when a wrapper command or CI job already lints without naming it. It does not disable the repo's selected commands or CI.

The fallback runs locally even for CI-backed reviews, before waiting for CI, and feeds failures through the same bounded agent repair flow. Repository lint commands retain their configured scope. The fallback does not apply fixes itself; the reviewer makes necessary edits. No repository lint config is written or replaced.

## Challenger review

CodeRabbit reviews are requested by Hydra after the owner enables the app. Automatic and automatic
incremental reviews are disabled. The assertive challenger checks bugs, tests and simpler code,
using the three shipped skills and the repository contributor review skill. It excludes
`package-lock.json`, keeps poems off and flags workflow changes, including unsafe privileged triggers.
